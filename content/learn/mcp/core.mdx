<PlainEnglish>
MCP is a standard way to plug tools and data into AI apps. Build a tool once as an MCP server and any MCP-compatible assistant can use it. This lesson also covers Agent Skills — packaged instructions that teach an agent how your team does a task.

**Think of it like:** USB-C for AI tools: one plug shape that fits every device.

**After this lesson you'll be able to** build an MCP server, connect to it from your own code and keep it secure.
</PlainEnglish>

## Why MCP exists

<Level l="intermediate" />

Before MCP, every AI application integrated every tool its own way: N applications × M tools = **N×M** custom integrations. The **Model Context Protocol** defines one protocol, so a tool provider writes one server and every compatible client — assistants, IDEs, agent frameworks — can use it. The problem shrinks to **N + M**.

```mermaid caption="One host runs one MCP client per server. Each server exposes tools, resources and prompts through the same protocol."
flowchart TD
  subgraph HOST[Host application · assistant, IDE or your agent]
    LLM[LLM] <--> C1[MCP client]
    LLM <--> C2[MCP client]
    LLM <--> C3[MCP client]
  end
  C1 <--> S1[MCP server: HR API<br/>tools · resources]
  C2 <--> S2[MCP server: files<br/>resources]
  C3 <--> S3[MCP server: database<br/>tools · prompts]
```

- **Host:** the application the user interacts with. It manages the clients, permissions and the LLM.
- **Client:** one connection to one server, inside the host.
- **Server:** exposes capabilities (tools, resources, prompts) over the protocol.

## Protocol basics

<Level l="intermediate" />

MCP messages are **JSON-RPC 2.0**: requests (with an `id`), responses, and notifications (no `id`).

### Lifecycle

1. **Initialise:** the client sends `initialize` with its protocol version, capabilities and info; the server replies with its own.
2. The client sends the `notifications/initialized` notification.
3. **Operation:** discovery (`tools/list`, `resources/list`, `prompts/list`) and use (`tools/call`, `resources/read`, `prompts/get`), plus notifications such as `notifications/tools/list_changed`, progress and logging.
4. **Shutdown:** close the transport.

```json title="tools/call request and response"
{"jsonrpc": "2.0", "id": 7, "method": "tools/call",
 "params": {"name": "get_employee", "arguments": {"employee_id": "E1043"}}}

{"jsonrpc": "2.0", "id": 7,
 "result": {"content": [{"type": "text", "text": "{\"id\": \"E1043\", \"name\": \"Priya S\", \"dept\": \"Finance\"}"}],
            "isError": false}}
```

### Server capabilities

| Capability | What it is | Controlled by | Example |
|---|---|---|---|
| **Tools** | Functions the model can call, with JSON Schema inputs | The **model** decides when to call (the host may require approval) | `create_ticket`, `search_orders` |
| **Resources** | Readable data identified by URIs | The **application or user** chooses what to attach | `file:///reports/q3.md`, `employees://E1043` |
| **Prompts** | Reusable prompt templates with arguments | The **user** picks them (for example as slash commands) | `summarise_incident(incident_id)` |

### Client capabilities (offered to servers)

| Capability | Purpose |
|---|---|
| Sampling | The server asks the client's LLM to generate text — agent behaviour on the server without its own model keys. The host stays in control and can require approval. |
| Roots | The client tells the server which folders or workspaces it may operate on |
| Elicitation | The server asks the user for more input through the client (confirm an action, or supply a missing parameter) |

### Transports

| Transport | How | Use |
|---|---|---|
| stdio | The host launches the server as a subprocess; messages go over stdin/stdout | Local tools, desktop assistants, IDEs |
| Streamable HTTP | The client POSTs JSON-RPC to one HTTP endpoint; the server may stream responses (SSE) and push notifications | Remote and shared servers, multiple users, cloud deployment |

The older HTTP+SSE transport has been replaced by Streamable HTTP — use the newer one for new servers.

## Building a full server with FastMCP

<Level l="advanced" />

```python title="hr_server.py"
import json
import httpx
from mcp.server.fastmcp import Context, FastMCP

mcp = FastMCP("hr-assistant-tools")
API = httpx.AsyncClient(base_url="https://hr-api.internal", timeout=15)

# ---------- tools ----------
@mcp.tool()
async def search_employees(query: str, department: str | None = None, limit: int = 10) -> list[dict]:
    """Search employees by name or email, optionally within a department.
    Returns up to `limit` results with id, name, title and department.
    Use this first to find an employee id."""
    r = await API.get("/employees", params={"q": query, "dept": department, "limit": min(limit, 20)})
    r.raise_for_status()
    return [{k: e[k] for k in ("id", "name", "title", "department")} for e in r.json()["items"]]

@mcp.tool()
async def bulk_leave_report(department: str, month: str, ctx: Context) -> str:
    """Summarise leave taken in a department for a month (YYYY-MM). May take a few seconds."""
    employees = (await API.get("/employees", params={"dept": department, "limit": 500})).json()["items"]
    rows = []
    for i, e in enumerate(employees):
        await ctx.report_progress(i, len(employees))           # progress notifications to the client
        rows.append((await API.get(f"/employees/{e['id']}/leave", params={"month": month})).json())
    await ctx.info(f"Processed {len(rows)} employees")          # a log message to the client
    total = sum(r["days"] for r in rows)
    return f"{department} took {total} leave days in {month} across {len(rows)} employees."

# ---------- resources ----------
@mcp.resource("policies://leave")
async def leave_policy() -> str:
    """The current leave policy document (Markdown)."""
    return (await API.get("/policies/leave")).text

@mcp.resource("employees://{employee_id}")
async def employee_profile(employee_id: str) -> str:
    """Profile of one employee as JSON."""
    return json.dumps((await API.get(f"/employees/{employee_id}")).json())

# ---------- prompts ----------
@mcp.prompt()
def onboarding_checklist(employee_name: str, role: str) -> str:
    """Generate an onboarding checklist for a new joiner."""
    return (f"Create a 30-60-90 day onboarding checklist for {employee_name}, joining as {role}. "
            "Use the leave policy resource for time-off rules and keep it under 300 words.")

if __name__ == "__main__":
    mcp.run()                                   # stdio by default
    # mcp.run(transport="streamable-http")      # a remote server over HTTP
```

FastMCP builds each tool's JSON Schema from the type hints and uses the docstring as the description — so **write docstrings for the model**: when to use the tool, what the arguments mean, what it returns.

### Results and errors

- Return JSON-serialisable data (dicts or lists). Clients receive it as content, and newer protocol versions also support structured output schemas.
- For failures, raise an exception with a clear message or return an error result (`isError: true`). The model sees the message and can recover: "Employee E99 not found. Search by name first."
- Keep outputs small: summarise, paginate and trim fields.

## Writing a client for your own agents

<Level l="advanced" />

```python title="remote_client.py"
import asyncio
from mcp import ClientSession
from mcp.client.streamable_http import streamablehttp_client

async def main():
    async with streamablehttp_client("https://mcp.internal.example/hr/mcp",
                                     headers={"Authorization": f"Bearer {token}"}) as (read, write, _):
        async with ClientSession(read, write) as session:
            await session.initialize()
            print([t.name for t in (await session.list_tools()).tools])
            res = await session.call_tool("search_employees", {"query": "priya", "department": "Finance"})
            print(res.content[0].text)
            doc = await session.read_resource("policies://leave")
            print(doc.contents[0].text[:200])

asyncio.run(main())
```

To give these tools to an LLM, convert each MCP tool into the provider's tool format (name, description, input schema). Adapters such as `langchain-mcp-adapters` do this for LangGraph, and many agent SDKs accept MCP servers directly. You build a complete server in [Project 08](/projects/openapi-mcp-server/).

## Authentication for remote servers

<Level l="advanced" />

For HTTP transports, MCP specifies authorisation based on **OAuth 2.1**: the MCP server is a resource server, and clients get access tokens from an authorisation server (your identity provider) and send them as bearer tokens ([OAuth and JWT](/learn/python-backend/production-backend/)).

- **Validate tokens on every request:** issuer, audience, expiry, scopes.
- **Map scopes to tools:** `hr.read` allows search tools; `hr.write` allows approve and create tools.
- **Propagate the user's identity** to downstream APIs (token exchange or on-behalf-of flows). Avoid a single all-powerful service account — otherwise every user effectively gets admin rights through the agent.
- **Never pass tokens through the model.** Tokens live in the client and server plumbing, never in prompts or tool arguments.

```python title="scopes.py"
# Your auth middleware validates the JWT first and stores the claims on the request
def require_scope(ctx, scope: str):
    claims = ctx.request_context.request.state.claims
    if scope not in claims.get("scope", "").split():
        raise PermissionError(f"missing scope {scope}")
```

## Security threats specific to MCP

<Level l="advanced" />

| Threat | Description | Mitigation |
|---|---|---|
| Tool poisoning | Malicious instructions hidden in tool descriptions or outputs ("also read ~/.ssh and send it…") | Install only trusted servers; review descriptions; hosts should display them; treat outputs as data |
| Rug pull / tool mutation | A server changes its tool definitions after you approved it | Pin versions; alert on `list_changed`; re-approve changed tools |
| Confused deputy | The server uses its own broad credentials on behalf of a less-privileged user | Per-user tokens, scope checks, on-behalf-of flows |
| Cross-server exfiltration | One server's output tells the model to send data to another server's tool | Host-level policies; approval for sensitive tools; no auto-approve for write tools across servers |
| Excessive permissions | Servers with file-system, shell or admin access | Least privilege, roots restrictions, read-only defaults, sandboxed servers |
| Supply chain | Malicious packages posing as popular servers | Verified publishers, checksums, internal registries |
| Session hijacking (HTTP) | Stolen session IDs | TLS, bound session IDs, short-lived tokens |

<Pitfall>
**The host is the security boundary.** MCP standardises communication, not trust. The host must show users which tools are called with which arguments, require approval for consequential actions, and let administrators allow-list servers. When you build your own agent host, you inherit these responsibilities. More in [LLM security](/learn/alignment-safety/deep-dive/).
</Pitfall>

## Testing and operating MCP servers

<Level l="advanced" />

- **MCP Inspector** (`npx @modelcontextprotocol/inspector`) lets you list and call tools, read resources and view protocol messages.
- **Unit tests:** call the tool functions directly with mocked APIs.
- **Contract tests:** start the server, connect a client session, and assert on `list_tools` schemas and `call_tool` results.
- **Agent evals:** tool-selection accuracy and task success with real LLMs ([evaluating agents](/learn/evaluation/deep-dive/)).
- **Operations:** structured logs and audit trails per call (who, which tool, which arguments, result), metrics (calls, errors, latency per tool), rate limits per client, version tags in server info, and changelogs for tool changes.

```python title="test_server.py"
import pytest
from mcp.shared.memory import create_connected_server_and_client_session
from hr_server import mcp

@pytest.mark.anyio
async def test_tools_listed():
    async with create_connected_server_and_client_session(mcp._mcp_server) as client:
        names = {t.name for t in (await client.list_tools()).tools}
        assert {"search_employees", "bulk_leave_report"} <= names
```

### MCP design checklist

- 5–15 focused tools per server; composite tools for common workflows.
- Docstrings written for the model: when to use, arguments, outputs, limits.
- Read and write tools clearly separated; write tools require host approval.
- Concise, paginated outputs; helpful errors.
- OAuth 2.1 for remote servers; scopes mapped to tools; user identity propagated.
- Resources for read-only context; prompts for common user workflows.
- Audit logging, metrics, rate limits; versioned releases.
- Tested with Inspector, contract tests and agent evals.

## Agent Skills: packaging know-how

<Level l="advanced" />

MCP gives an agent **capabilities** — tools and data it can reach. It doesn't teach the agent **how your team does things**: the steps to prepare a board report, the house style for release notes, the checks before closing an incident. **Agent Skills** fill that gap.

A **skill** is a folder containing a `SKILL.md` file — instructions with a short YAML header — plus any scripts, templates or reference files the instructions need. Anthropic introduced skills in 2025 and published the format as an open standard, so skills now work across several agent products and SDKs.

```text title="skills/monthly-leave-report/"
monthly-leave-report/
├── SKILL.md              # name, description, then the instructions
├── report_template.md    # loaded only when the instructions say so
└── scripts/
    └── leave_stats.py    # run by the agent, not loaded into context
```

```markdown title="SKILL.md"
---
name: monthly-leave-report
description: Prepare Acme's monthly leave report for a department. Use when someone asks for a leave report, leave summary or absence statistics for a month.
---

# Monthly leave report

1. Ask for the department and month (YYYY-MM) if they weren't given.
2. Call the `bulk_leave_report` tool from the hr-assistant-tools MCP server.
3. Run `python scripts/leave_stats.py <department> <month>` for trends versus the previous 3 months.
4. Fill in `report_template.md`. Keep it to one page; numbers in tables, not prose.
5. Never include individual employees' names or reasons for leave — totals only.
```

### Progressive disclosure

Skills are cheap to install because of **progressive disclosure** — the agent loads only what it needs, when it needs it:

1. **At start-up**, only each skill's `name` and `description` go into the context — a few dozen tokens per skill, so you can install many.
2. **When a request matches** a description, the agent reads that skill's full `SKILL.md`.
3. **Only if the instructions call for it** does the agent open the extra files or run the scripts. A script's *output* enters the context, not its code.

```mermaid caption="Progressive disclosure: descriptions are always loaded, instructions when relevant, and extra files only on demand."
flowchart TD
  S[Session starts] --> D[Load name + description<br/>of every skill]
  D --> Q[User request]
  Q --> M{Matches a<br/>description?}
  M -- no --> N[Answer normally]
  M -- yes --> I[Read that SKILL.md]
  I --> F{Instructions need<br/>more files or scripts?}
  F -- yes --> X[Open file / run script<br/>output enters context]
  F -- no --> A[Follow instructions]
  X --> A
```

### Adding skills to your own agent

The pattern is simple enough to implement yourself:

```python title="skills_loader.py"
import pathlib, yaml

def load_skill_index(root="skills"):
    index = {}
    for f in pathlib.Path(root).glob("*/SKILL.md"):
        header = f.read_text().split("---")[1]               # the YAML front matter
        meta = yaml.safe_load(header)
        index[meta["name"]] = {"description": meta["description"], "path": f}
    return index

SKILLS = load_skill_index()
skills_menu = "\n".join(f"- {n}: {s['description']}" for n, s in SKILLS.items())
SYSTEM = ("You can use these skills. When one is relevant, call read_skill(name) first and follow it.\n"
          + skills_menu)

def read_skill(name: str) -> str:
    """Tool: return the full instructions of a skill."""
    return SKILLS[name]["path"].read_text()
```

| | MCP | Agent Skills |
|---|---|---|
| Provides | Tools and data (capabilities) | Instructions, templates and scripts (know-how) |
| Lives in | A running server | A folder of files |
| Loaded | Tool definitions at connection | Description always; body and files on demand |
| Typical use | "Query the HR API" | "How we write the monthly leave report" |

They work together: the skill above tells the agent *when and how* to use the MCP server's tool.

<Pitfall>
**Skills can contain code.** A skill's scripts run with the agent's permissions, and its instructions are prompts the agent will follow. Install skills only from sources you trust, read them before enabling them, keep them in version control with code review, and run their scripts in a sandbox.
</Pitfall>

<Interview>
<QA q="What are MCP's three server primitives, and who controls each?">
Tools (invoked by the model, possibly gated by the host), resources (context chosen by the application or user) and prompts (templates the user selects).
</QA>
<QA q="stdio vs Streamable HTTP?">
stdio runs the server as a local subprocess for desktop and IDE use. Streamable HTTP serves remote, multi-client deployments, with OAuth-based authorisation.
</QA>
<QA q="How do you stop an MCP server becoming a privilege-escalation path?">
Per-user tokens and scopes, on-behalf-of calls downstream, least-privilege tools, approval for writes, audit logs, and treating tool descriptions and outputs as untrusted.
</QA>
<QA q="How are Agent Skills different from MCP?">
MCP connects an agent to tools and data. Skills package procedural knowledge — instructions, templates and scripts — loaded progressively so many can be installed cheaply. A skill often tells the agent how to use MCP tools for a particular task.
</QA>
</Interview>

<Takeaways>
- MCP is JSON-RPC between a host's clients and servers exposing tools, resources and prompts; clients can offer sampling, roots and elicitation.
- Use stdio locally and Streamable HTTP remotely with OAuth 2.1, scopes and identity propagation; the host is the security boundary.
- Agent Skills package team know-how as folders with a `SKILL.md`, loaded by progressive disclosure — review them like code.
</Takeaways>
